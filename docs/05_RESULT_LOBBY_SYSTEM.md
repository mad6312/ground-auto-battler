# グラウンド・オートバトラー 正式仕様書 - 05: 最終リザルト・ロビー・システム仕様

---

## 1. 最終リザルト・ゲーム終了仕様

### 1.1. ゲーム終了および優勝判定
* **単独優勝**: 生存プレイヤーが **1名** になった時点でゲーム終了となり、そのプレイヤーが1位（単独優勝）となる。
* **同時優勝（全員同時全滅）**: 最終ラウンドに残っていたプレイヤー全員が同時に敗北し、生存者が0名になった場合は、その最終ラウンドで同時に脱落した全員を **1位（同時優勝）** とする。
* **例外処理（全員切断または勝者切断時の優勝者なし）**:
  * 生存者がいる状態で全生存者が切断等により0名になった場合、残された脱落プレイヤーを不当に繰り上げ優勝者とはせず、**例外的に「優勝者なし」として処理し、VICTORYボックスは絶対に非表示**とする。
  * 最終ラウンドで単独勝者が決定した後に、結果閲覧中の勝者が切断した場合も同様に、敗北済みの脱落者が繰り上げ1位になることはなく「優勝者なし」として扱われる。
  * 順位表においても脱落者が1stとして表示されることはなく、先頭行に「（優勝者なし）」が順位`-`・ライフ`-`で表示され、直後の脱落者は2nd以降から順位付けされる。
* **バトル終了とゲーム終了移行（要件）**:
  * 優勝者が決定する最終ラウンドであっても、**バトルの実行前に最終リザルト画面へ早期遷移することは絶対にない**。
  * 通常通りバトル演出および対戦結果モーダルを確認した後、**各プレイヤーが自発的に「次へ」を押した段階で最終リザルト画面へ遷移**する（閲覧中に他プレイヤーの操作によって強制遷移されることはない）。
* **切断による即時ゲーム終了**: プレイヤーの切断により生存者が1名以下になった場合は、即座に最終リザルト画面へ遷移する。
* **モーダル全閉によるソフトロック防止**: 最終リザルト画面表示時、手札超過モーダル、確認ダイアログ、Tipsモーダルなど開いている全てのモーダルは一括で閉じられ、手札超過準備フラグ等の入力待機フラグも完全初期化される。最終リザルト画面は最前面レイヤー（`z-index: 1500`）に配置される。

### 1.2. 最終順位の決定規則
順位は以下の優先順位に従って厳格に決定される。同順位のプレイヤーが存在する場合、次の順位番号はその人数分だけ繰り下げられる。

1. **生存プレイヤー**: 残りライフ数に関わらず上位（単独生存時は1位）。
2. **強制終了時の生存者**: 残りライフの降順で順位付け（同ライフの場合は同順位）。**残りライフ同値で1位が複数名いる場合は同時優勝扱い**となる。
3. **脱落プレイヤー**: 脱落したラウンド番号（`eliminatedRound`）の降順で整列（遅いラウンドで脱落したプレイヤーほど上位）。同じラウンドで脱落したプレイヤー同士は **同順位** とする。ライフ表示は赤色ハートで表示される。
4. **切断プレイヤー**: ゲーム途中に切断したプレイヤーは、最下位行にグレー色で表示される。

### 1.3. 順位表記とカラー設定
* **1st**: 金色 (`#facc15`, 太字)
* **2nd**: 銀色 (`#e2e8f0`, 太字)
* **3rd**: 銅色 (`#cd7f32`, 太字)
* **4th以下**: 白色 (`#ffffff`, 太字)
* **切断**: グレー (`#94a3b8`, イタリック)

### 1.4. 残りライフの表示色
順位表に表示される残りライフ（例: `♥♥♥♥♥`）は、白色ではなく**ゲーム中と同じ赤色 (`#ef4444`)** で表示される。

### 1.5. 切断プレイヤーの表示維持
ゲーム途中に切断したプレイヤーについても最終リザルト画面から除外せず、以下の形式で行を保持して表示する。

| 順位 | プレイヤー名 | 残りライフ |
| :---: | :--- | :---: |
| **切断** | 切断したプレイヤー名 | **-** |

### 1.6. 優勝者専用ハイライト演出（VICTORYボックス）
優勝者が決定した際、王冠アイコン（👑）と黄金の光彩アニメーションによる **VICTORY ボックス** が画面上部に表示される。
* **単独優勝時**: 優勝者の名前が単独で表示される。
* **同時優勝時（通常・強制終了含む）**: 同時優勝となったプレイヤー全員の名前が連名（`〇〇 & △△`）で強調表示される。
* **優勝者なし時**: VICTORYボックスは非表示となる。

### 1.7. バトルリザルト「次へ」ボタンの1.5倍拡大仕様（改修後正式仕様）
* バトルリザルト画面に表示される大型「次へ」ボタン（`.btn-result-next-wide`）は、**横幅を従来の1.5倍（`width: 240px`）に拡大**して表示される。
* ボタン文字サイズも `1.15rem`、文字間隔 `2px` へ強化され、対戦後の次フェーズ移行操作が直感的かつ確実に実行できる。

### 1.8. 再戦・退出操作の一元化および2試合目以降の進行保証（要件）
* **不正操作・不正復活の完全遮断**:
  * ゲーム進行中（決着前）における `lobby:rematch` や `lobby:leave` の不正実行はサーバー側で完全に無視・破棄される。
* **ゲーム終了処理の一元化**:
  * 決着確定後にいずれかのプレイヤーが「再戦」または「退出」を押下した際、サーバー側は一元化された終了処理（`endGameCompletely`）を直ちに実行する。
  * これにより、全参加者へ最終順位データ（`game:ended`）が送出され、全員の参加フラグ（`isEntered`）が安全に `false` に初期化される。
  * その後、押下したプレイヤー本人のみが「再戦（エントリー状態）」または「退出（未エントリー状態）」としてロビーに遷移する。
  * **結果画面残留者の保護**: 前試合の結果画面に残っているプレイヤーが意図せず自動エントリーされたり、次試合に勝手に巻き込まれることは絶対にない。
* **「再戦」ボタン**:
  * 押した本人のみが即座にロビー画面へ遷移し、新品の初期ライフ（5）・初期ゴールド（20G）・空の手札・出撃枠の状態で再戦エントリー状態（参加中）となる。ホストが再戦を押した場合はホスト権を維持する。
  * ロビーのエントリー人数が10人に達している場合、未エントリープレイヤーの再戦は受け付けられない。
* **「退出」ボタン**:
  * 押した本人が未エントリー状態で確実にロビー画面へ復帰する。
* **2試合目以降のゲーム開始保証**:
  * 1試合目終了後にゲームロビー画面へ戻った場合でも、ホストの画面には参加人数が2人以上になった時点で確実に「ゲーム開始」ボタンが表示される。
  * ホストが「ゲーム開始」ボタンを押下した際、前試合の残留データに影響されることなく、全参加プレイヤーの初期ショップ・初期配布カードが新規生成され、第2試合以降が正常に開始される。

## 2. ロビー・エントリー機能

### 2.1. エントリーボタン
* 「参加する」と「参加キャンセル」を切り替えるトグルボタン。
* ロビー画面表示中は常時クリック可能であり、接続・切断が発生しても動作が保証される。
* **10人上限の厳格適用**: 現在のエントリー人数が10人に達している場合、未エントリーのプレイヤーが「参加する」および「再戦」を押してもエントリーは受け付けられない。

### 2.2. ロビー画面における右上ボタンの完全固定配置（改修後正式仕様）
* ロビー画面表示中はヘッダー左上HUDクラスター（`#hud-dashboard-cluster`）自体が完全に非表示化（`hidden`）される。
* この際、画面上部の「💡 Tips」ボタンおよび「⚙ 設定」ボタン（`.hud-right-group`）が左上へ流れて表示されることはなく、**`margin-left: auto;` により常に画面右上に整然と固定配置**される。

### 2.3. 切断・再接続時のクライアント完全初期化
クライアントが切断・再接続した場合、クライアント内の手札・ショップ・スロット・全モーダル（`gameOverModal` 含む）・入力フラグ等の内部状態は自動的に完全リセットされ、未参加状態でロビー画面へ復帰する。

### 2.4. 参加状況とバッジ表示
* 現在のエントリー人数（`○ / 10`）をリアルタイム表示。
* 状態バッジ: `未エントリー` / `参加中... 他のプレイヤーを待っています` を同期。

### 2.5. ホスト権限と自動委譲規約
* 最初に接続したプレイヤーが自動的にホストとなる。
* **結果画面閲覧中のホスト権限維持（要件厳格化）**:
  * 最終リザルト画面において、ホストが「再戦」または「退出」を押下する前に、他のプレイヤーが先に「再戦」を押下してロビーへ戻った場合でも、**ホスト権がそのプレイヤーへ勝手に譲渡されることは絶対にない**。
  * ホストが「再戦」を押下した場合は、**ホスト権を維持したままロビー画面へ遷移し再戦処理を進行**する。
* **自動委譲の限定条件**:
  * ホスト権限の自動委譲が行われる契機は、以下の2点に厳格限定される。
    1. **ホストが切断・離脱した場合**: 残存プレイヤーの中から、エントリー中のプレイヤーを最優先（いなければ接続順）として即座に自動委譲される。
    2. **ホストが自発的に「退出」を押下した場合**: ホスト自身が参加を辞退したため、残存プレイヤーへ即座に自動委譲される。
* エントリー人数が2人以上になると、ホストにのみ「ゲーム開始」ボタンが表示され、クリックでゲームを開始できる。

## 3. 「Tips」機能（ガイドモーダル）

### 3.1. 「Tips」ボタン
* 画面右上の「⚙ 設定」ボタンの左隣に **「💡 Tips」** ボタンを配置。
* ロビー画面およびゲームプレイ中の両方から利用可能。

### 3.2. ウィンドウサイズ固定とレイアウト
タブを切り替えてもウィンドウサイズが伸縮しないよう、モーダル全体の幅（760px）と高さ（570px）が固定されている。コンテンツはウィンドウ内で縦方向中央に配置される。

### 3.3. タブ構成と表示内容

#### ① 「属性」タブ
上部に以下の2つの**三角形（△）型属性相性図**を横並びで表示する。
* **属性相性図 1**: 火 ➔ 氷 ➔ 風 ➔ 火（火は氷に強く、氷は風に強く、風は火に強い）
* **属性相性図 2**: 雷 ➔ 水 ➔ 地 ➔ 雷（雷は水に強く、水は地に強く、地は雷に強い）

下部説明文:
> 属性は、攻撃時の弱点・耐性判定に関与します。  
> **弱点属性への攻撃：** 攻撃側が与えるダメージが2倍になります。  
> **耐性属性への攻撃：** 攻撃側が与えるダメージが1/2になります。

#### ② 「種族」タブ
上部説明文:
> 手札に同種族カードが2枚以上ある場合、その種族のカードが1枚増えるごとに、対象スタッツの補正倍率が10%または5%ずつ上昇します。

下部に種族別の補正スタッツ・倍率表を表示する。

#### ③ 「合成」タブ（カードUI合成例の日英3:2完全表示）
上部説明文:
> レアリティと種族が同じカード同士は合成することができます。

中央に合成例を実際のカードUI（日英分離2行表示、日本語:英語＝3:2、基本サイズ一定、英語本来の表記維持、中央揃え）を用いて横並びで表示する。
* **合成元**: 焔刃のエルフ / Flameblade Elf [火/エルフ/★1] ❤2 / ⚔1 / ⚡7
* **記号**: ＋
* **素材**: 霜精のエルフ / Frost-Spirited Elf [氷/エルフ/★1] ❤1 / ⚔3 / ⚡6
* **記号**: ＝
* **合成後**: 焔刃のエルフ / Flameblade Elf [火/エルフ/★2] ❤3 / ⚔4 / ⚡13（ゴールド発光枠 `synth-highlight-gold`）

下部説明文:
> 合成の素材にするカードを、合成元にするカードへドラッグ＆ドロップすることで、合成後のカードの各スタッツがそれぞれの合計値になります。  
> また、カード名・レアリティ・属性・種族は、合成元カードの情報が引き継がれ、★バッジの数値が合算されます。

## 4. 設定モーダル（画面右上 ⚙設定）

* **プレイヤー名変更**:
  * ラベル表示: **「名前:」**
  * ボタン表示: **「変更」**（ボタン内の文字が改行されず1行で表示）
  * マッチング維持の原則: プレイヤーが名前を変更しても、すでに決定している対戦相手のペアリングが再抽選されることは絶対にない。準備フェーズ中のみ相手へ新しい名前が通知される。ゼロ幅スペース等の不可視文字・制御文字は自動サニタイズされる。
* **ゲームの強制終了**:
  * ゲーム進行中、ホストにのみ「ゲームを強制終了」ボタンが表示される。
  * クリック時、ホスト設定モーダルは即座に閉じられ、確認ダイアログが単独で表示される。
  * 承認されるとその時点の生存プレイヤーを残りライフ降順（同値は同順位）で順位付けし、その後に脱落者を脱落ラウンド順で配置してゲーム終了画面へ移行する。

## 5. 入力操作・ドラッグシステムの設計規約

* **Pointer Eventsカスタムドラッグ**:
  ブラウザネイティブのDrag & Dropを使用せず、Pointer Events（`pointerdown`, `pointermove`, `pointerup`, `pointercancel`）によるカスタムドラッグを採用する。
* **カードイラスト領域のドラッグ仕様**:
  ブラウザ標準の画像ドラッグ機能は全カード画像で完全に阻止（`-webkit-user-drag: none; pointer-events: none;`）する。
  **カードイラスト領域（`.card-art-container`）をドラッグした場合でも、通常どおりカードUI全体のカスタムドラッグが発火し、自由に移動・配置できる**。
* **手札下部ドロップ判定範囲の拡張**:
  ショップや市場から手札へドラッグ＆ドロップしてカードを購入する際、手札UIコンテナ（`.hand-section-wrapper`）の上端より下側であれば、**手札UIより下の画面下端領域にドロップした場合でも購入処理が確実に成立**する。
* **ウィンドウ監視によるドラッグ追従と安全解放**:
  * イベントは `window` 単位で一括監視され、ドラッグ中にDOM再描画が発生してもゴースト要素が取り残されることはない。
  * マウスボタンが離された状態（`e.buttons === 0`）を検知した場合、およびブラウザウィンドウからフォーカスが離脱（`blur`）した場合は、直ちにドラッグを安全にキャンセルし、意図しない自動売却やカード消失を防止する。
